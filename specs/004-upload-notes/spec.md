# Feature Specification: 批量上传 Markdown 笔记

**Feature Branch**: `[004-upload-notes]`

**Created**: 2026-09-22

**Status**: Draft

**Input**: User description: "在/en/console/notes 页面"New Note"按钮左边增加"Upload Notes"按钮，点击进入笔记上传页面。在该页面上方展示文件选择按钮，点击弹出系统文件选择框。提示用户选择一个或多个markdown格式的文件。在用户选择并确认后，利用浏览器文件系统API在页面下方展示上传队列列表。列表中展示文件名称、后缀名、文件大小、修改时间和操作列。在最右侧操作列展示移除和上传状态指示标签。点击移除将当前文件从上传队列中移除。页面上方文件选择框旁边展示开始上传按钮，然后批量上传文件（最多批量上传3个文件，代码常量）。每上传一个文件完成后，更新上传队列中该文件的上传状态指示标签。区分待上传、成功、失败等状态。若失败时鼠标悬停可以展示简短错误。上传队列最多30个文件，每个文件大小不超过2M。暂时以常量形式硬编码到代码里。注意上传时需要确定当前/en/console/notes页面展示的目录层级，以正确设置新上传文件的父级目录。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 批量选择并上传 Markdown 文件创建笔记 (Priority: P1)

作为笔记控制台的用户，我希望在笔记列表页通过"Upload Notes"入口进入上传页面，一次性选择多个本地 Markdown 文件并批量上传，使每个文件自动创建为当前目录下的一篇新笔记，从而免去逐篇手动新建、粘贴内容的重复劳动。

**Why this priority**: 这是本功能的核心价值——批量导入笔记；没有它其余场景（移除、状态提示）都没有意义，也是唯一能独立交付价值的最小闭环。

**Independent Test**: 在笔记列表页点击"Upload Notes"，进入上传页面后选择若干合规的 `.md` 文件并确认，点击"开始上传"，等待队列中所有文件状态变为"成功"，返回笔记列表页可看到对应数量的新笔记出现在当前目录下。

**Acceptance Scenarios**:

1. **Given** 用户在 `/en/console/notes` 页面（根目录，未选中任何子目录），**When** 用户点击"New Note"按钮左侧的"Upload Notes"按钮，**Then** 页面跳转到笔记上传页面，且页面记住来源目录为根目录。
2. **Given** 用户已进入上传页面，**When** 用户点击文件选择按钮，**Then** 系统弹出文件选择框，仅允许选择 Markdown 格式文件，且支持一次选中多个文件。
3. **Given** 用户在文件选择框中选中 5 个合规的 `.md` 文件并确认，**When** 选择完成，**Then** 页面下方的上传队列列表中出现 5 行记录，每行展示文件名、后缀名、文件大小、修改时间，以及初始状态为"待上传"。
4. **Given** 上传队列中已有若干"待上传"文件，**When** 用户点击"开始上传"按钮，**Then** 系统按最多 3 个文件同时上传的方式批量处理队列，其余文件保持"待上传"直至获得处理机会。
5. **Given** 某个文件上传完成（无论成功或失败），**When** 处理结束，**Then** 该文件在队列中的状态标签更新为"成功"或"失败"，不影响其他文件的状态。
6. **Given** 全部文件上传完成，**When** 用户返回 `/en/console/notes` 当前所在目录，**Then** 每个上传成功的文件都作为一篇新笔记出现在该目录下，笔记标题取自文件名（不含扩展名），正文为文件内容。
7. **Given** 用户此前是从某个子目录（例如目录 A）点击进入的上传页面，**When** 文件上传成功，**Then** 新建笔记的父级目录为目录 A，而非根目录。

---

### User Story 2 - 上传前从队列中移除文件 (Priority: P2)

作为用户，我希望在开始上传之前，能够将误选的文件从上传队列中移除，避免创建不需要的笔记。

**Why this priority**: 提升操作容错性，属于核心上传流程的重要补充，但没有它用户仍可通过重新选择文件规避，不影响 MVP 的基本可用性。

**Independent Test**: 选择多个文件进入队列后，点击其中一个文件的"移除"操作，确认该文件从队列中消失且不参与后续上传，同时不影响队列中其他文件。

**Acceptance Scenarios**:

1. **Given** 上传队列中有多个"待上传"状态的文件，**When** 用户点击某一行的"移除"，**Then** 该文件立即从队列列表中消失，队列总数相应减少。
2. **Given** 用户已点击"开始上传"，某文件已进入上传中或已完成（成功/失败），**When** 用户尝试移除该文件，**Then** 系统仅允许移除尚未开始上传的文件，已在处理中或已完成的文件的移除操作不可用。

---

### User Story 3 - 查看失败文件的简短错误原因 (Priority: P3)

作为用户，我希望在某个文件上传失败时，能够快速了解失败原因，以便判断是否需要修改文件后重试。

**Why this priority**: 提升可用性与可诊断性，是失败状态的自然延伸，但不阻塞成功路径的基本使用。

**Acceptance Scenarios**:

1. **Given** 队列中某文件状态为"失败"，**When** 用户将鼠标悬停在该状态标签上，**Then** 系统展示一条简短的错误说明（例如"文件超过大小限制"“名称已存在”"上传失败，请重试"）。
2. **Given** 用户移开鼠标，**When** 悬停结束，**Then** 错误提示消失，不遮挡列表其他内容。

---

### Edge Cases

- 用户在文件选择框中一次性选择的文件数量加上队列中已有的文件数量超过 30 个上限：系统只接受未超出上限的部分，并提示用户已达到队列数量上限。
- 用户选择的单个文件大小超过 2MB：该文件不计入可上传队列（或在队列中直接标记为失败/不可上传状态），并提示大小超限。
- 用户选择的文件不是 Markdown 格式：文件选择框按 Markdown 格式过滤，非法格式文件不会进入队列。
- 用户在同一目录下上传的文件名（去除扩展名后的标题）与该目录内已有的笔记或子目录同名：该文件被标记为上传失败，并提示名称冲突。
- 队列为空时点击"开始上传"：按钮不可用或不产生任何上传行为。
- 上传过程中用户离开或刷新上传页面：未完成的上传中止，已成功创建的笔记保留，页面重新进入后队列清空，需要用户重新选择文件。
- 用户在上传页面未做任何目录跳转、直接通过地址栏或收藏夹进入：新笔记的父级目录视为根目录（无上级目录）。
- 同一批次中部分文件成功、部分失败：不进行整体回滚，各文件的处理结果相互独立。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须在 `/{lang}/console/notes` 页面的"New Note"按钮左侧新增"Upload Notes"按钮。
- **FR-002**: 系统必须在用户点击"Upload Notes"后，跳转到独立的笔记上传页面，并携带用户当前浏览的目录层级信息（即当前所在的父级目录）。
- **FR-003**: 上传页面顶部必须提供一个文件选择入口，点击后弹出系统文件选择框，且该选择框限定用户只能选择 Markdown 格式的文件，并支持一次选择多个文件。
- **FR-004**: 用户完成文件选择并确认后，系统必须在页面下方将所选文件加入上传队列列表并展示。
- **FR-005**: 上传队列列表的每一行必须展示：文件名称、文件后缀名、文件大小、文件的最后修改时间，以及一个操作列。
- **FR-006**: 操作列必须在最右侧同时提供"移除"操作和当前文件的上传状态指示标签。
- **FR-007**: 用户点击某文件的"移除"操作时，系统必须将该文件从上传队列中删除；已开始上传或已完成的文件不可被移除。
- **FR-008**: 上传页面顶部的文件选择入口旁边必须提供"开始上传"按钮，点击后触发队列中"待上传"文件的批量上传。
- **FR-009**: 系统必须限制同一时刻最多有 3 个文件处于上传中状态（硬编码常量），超出并发上限的文件保持"待上传"，待有空闲名额后依次处理。
- **FR-010**: 每个文件处理完成后，系统必须将该文件在队列中的状态标签更新为"成功"或"失败"，并且该更新不得影响队列中其他文件当前的状态。
- **FR-011**: 上传状态标签必须至少区分"待上传""成功""失败"三种状态，且在上传过程中清晰可辨。
- **FR-012**: 当某文件状态为"失败"时，用户将鼠标悬停在该状态标签上，系统必须展示一条简短的错误说明。
- **FR-013**: 系统必须限制单个上传队列中的文件总数不超过 30 个（硬编码常量），超出部分不得加入队列。
- **FR-014**: 系统必须限制单个待上传文件的大小不超过 2MB（硬编码常量），超出限制的文件不得成功上传，并标记为失败或拒绝加入队列。
- **FR-015**: 系统必须使用用户进入上传页面前所在的目录层级作为新建笔记的父级目录；若用户来自根目录，则新建笔记归属根目录（无父级目录）。
- **FR-016**: 每个成功上传的 Markdown 文件必须在系统中创建为一篇独立的新笔记，笔记标题取自文件名（去除扩展名），正文内容取自文件的文本内容。
- **FR-017**: 若某文件对应的笔记标题与目标目录下已存在的笔记或子目录同名，系统必须拒绝创建该笔记，并将该文件标记为失败。

### Key Entities *(include if feature involves data)*

- **笔记（Note）**：批量上传的最终产出物，每个合规 Markdown 文件对应一篇新笔记，归属于用户触发上传时所在的目录（父级笔记/目录），标题来自文件名，正文来自文件内容。
- **上传队列项（Upload Queue Item）**：上传页面内的临时、仅页面生命周期内存在的状态记录，代表一个被选中的待处理文件，包含文件名、后缀名、大小、修改时间、当前状态（待上传/成功/失败）及失败原因，不在用户离开或刷新页面后保留。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户可以在同一个上传页面内，一次性选择并处理最多 30 个 Markdown 文件，无需切换页面或重复进入上传流程。
- **SC-002**: 每个文件从进入上传状态到状态标签更新为"成功"或"失败"，用户无需刷新页面即可看到结果。
- **SC-003**: 对于大小不超过 2MB 且命名不冲突的合规 Markdown 文件，上传成功后 100% 能在对应目录下找到同名的新笔记。
- **SC-004**: 用户在不满足限制条件（超过数量/大小限制、格式不符、名称冲突）时，能够在不查阅文档的情况下，通过界面提示理解为何该文件未被成功上传。
- **SC-005**: 用户从点击"Upload Notes"到完成一批文件上传，全程停留在同一上传页面，无需返回笔记列表页确认目录层级是否正确。

## Assumptions

- 新创建的笔记默认不关联任何频道（channel）且为未发布的草稿状态，与当前手动新建笔记的默认行为保持一致；用户可上传完成后自行编辑该笔记以设置频道与发布状态。
- 若上传文件对应的标题与目标目录下已有笔记/子目录重名，沿用现有目录创建时"同级不允许重名"的约束，将该文件标记为失败，不覆盖已有内容。
- 文件选择入口仅接受 `.md` / `.markdown` 后缀的文件；非法格式文件在系统文件选择框阶段即被过滤，不进入应用内校验流程。
- "开始上传"为显式触发动作，文件加入队列后不会自动开始上传，需用户主动点击。
- 上传队列及其中每个文件的状态均为页面级临时状态，不做持久化；用户离开或刷新上传页面后队列清空，已成功创建的笔记不受影响。
- 30 个文件的队列上限、2MB 的单文件大小上限、3 个文件的并发上传上限均为产品预设的固定值，暂不对用户开放配置。
- 上传页面仅服务于新建笔记场景，不支持通过上传覆盖已存在笔记的内容（即同名冲突时不做"更新已有笔记"的语义）。
